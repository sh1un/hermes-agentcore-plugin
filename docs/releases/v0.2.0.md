# v0.2.0: Identity-managed Cognito tokens

Adds `mode=vault_gateway` for an existing Hermes deployment. The platform hosts
the callback and session binding; AgentCore Identity stores Cognito tokens and
handles refresh. The agent retrieves access tokens and calls Gateway.

## Login flow

1. Start sign-in from Slack App Home.
2. Complete Cognito/Google login in the browser.
3. Complete the platform's Slack OIDC identity check in the browser.
4. Return to Home and select **Refresh sign-in** to retrieve the result.

Binding requires the same verified Slack workspace/member that started the
request. Google and Slack accounts do not need matching email addresses: Alice
may bind a login completed with Bob's Google account by verifying as Alice in
Slack. Bob verifying as Bob cannot complete Alice's request. A URL without a
valid matching Slack session cannot complete binding.

The browser's Slack identity check replaces portal mode's separate Slack
**Confirm** action in this mode. Refresh reads the result; it grants no binding
authority. The platform may reuse an existing Slack browser session.

## Integration

- Use `examples/vault-gateway.toml` and provide the platform binding endpoint.
- Keep Agent IAM roles and policies in the Agent Owner's infrastructure.
- Do not grant the agent `CompleteResourceTokenAuth` or the binder role.
- The agent needs no inbound callback port. Runtime images support AMD64/ARM64.
- Existing portal and direct modes retain their behavior. Select the new mode
  explicitly; a version update alone does not migrate configuration.

## Validation status

Source version prepared; no v0.2.0 release tag or deployment is implied.
Tests use mocked AWS APIs. Platform tests cover the four binding scenarios with
signed Slack JWTs; plugin tests cover pending refresh and user isolation.
Live Cognito, Slack, token refresh and Jira calls still need staging acceptance.
A trusted Agent supplies the initiating Slack ID; this flow does not protect
existing grants from a fully compromised authorized Agent.
